# Единый каталог контрактов

Сейчас здесь только правила и заготовки каталогов. Действующих OpenAPI-схем нет; endpoints и модели ещё не согласованы.

## Структура V1

- `identity/` — отдельный сервис входа и сессий.
- `media/` — отдельный файловый сервис.
- `core/` — API основного backend; подкаталоги community, planning, communication, training, collaboration, notifications разделяют владение контрактами внутренних модулей.
- `frontend/` — декларативные схемы локальных представлений и межмодульных интерфейсов. Это не второй набор копий HTTP DTO; они генерируются из core/identity/media.
- `shared/` — технические ошибки, курсоры и метаданные, не общая предметная модель.

После согласования: `openapi.yaml` у сервисов, схемы по модулям через ссылки; события/WebSocket описываются подходящими схемами в том же дереве. Наличие событий не требует внешнего брокера. Runtime MFE manifest в V1 отсутствует. Готовность разделения обеспечивают публичные границы контрактов, а не сетевые вызовы внутри core.

## Только генерация моделей

- HTTP DTO, клиенты, серверные интерфейсы и runtime validators генерируются из согласованных контрактов в этом каталоге.
- Модели событий и WebSocket генерируются из соответствующих схем; frontend не копирует backend-типы вручную.
- Persisted/ORM-модели генерируются из декларативной схемы БД своего сервиса/модуля. Не превращать публичный OpenAPI в физическую схему таблиц и не отдавать ORM-сущность как API-ответ.
- Предметные и frontend view-модели, если нужны отдельные формы данных, также имеют декларативную схему и генерируются; вручную пишутся поведение, функции, политики и mapping между сгенерированными формами. Не обходить требование ручным DTO с названием state/view-model.
- Схемы моделей БД и миграции принадлежат сервису; документация — `techDocs/services/<id>/`. Контракты обмена принадлежат только соответствующему каталогу `openApi/` по структуре выше.
- Конкретные генераторы выбираются после утверждения языка и схем, проверяются пробной генерацией и фиксируются по версиям. Не утверждать, что один генератор покрывает все категории.

Изменение: схема → lint/валидация → проверка совместимости → генерация → компиляция → тест producer/consumer → документация. Generated-файлы не редактировать. В CI повторная генерация должна давать нулевой diff (либо идентичный build-artifact при принятой политике); стратегию хранения выбрать на DevOps-этапе.

Версионировать контракты, различать optional/null, единицы измерения, зоны времени, ошибки, пагинацию, авторизацию и идемпотентность. Удаление поля/смена типа требует миграции потребителей. События содержат ID, тип, версию, источник, aggregate ID/version, время и correlation ID; не включать лишние персональные данные. Контракты shared не становятся общей базой всех предметных сущностей.

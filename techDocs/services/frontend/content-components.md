# FE-20 · Message, EventCard, PostCard, WorkoutEntry

Статус: предложение FE-20 согласовано сообщением «согласовано». Четыре набора Figma дополнены, собраны 12 проверочных листов Light/Dark. Дизайн ожидает визуальной приёмки; код FE-20 не начат.

## Исходный дизайн

[Страница библиотеки в Figma](https://www.figma.com/design/qTLyRxJkaRvicTercpHUqr?node-id=17-466), направление 02 «Круг». Используются существующие Light/Dark-токены и общие Button; продуктовые экраны R2–R5 в FE-20 не создаются.

| Набор        | Существующие варианты                              | ID набора |
| ------------ | -------------------------------------------------- | --------- |
| Message      | Incoming, Sent, Sending, Failed                    | `17:617`  |
| EventCard    | Invited, Joined, Cancelled                         | `17:664`  |
| PostCard     | Default, Liked                                     | `17:704`  |
| WorkoutEntry | Mobile Strength/Distance, Desktop Strength/Summary | `17:749`  |

Message уже различает входящее и исходящее сообщение цветом и содержит доставку/ошибку. EventCard показывает приглашение, участие и отмену. PostCard меняет счётчик реакции. WorkoutEntry использует карточки шириной 358 px на mobile и строки шириной 920 px на desktop.

Аудит исходника выявил: только светлые экземпляры в самих наборах; отсутствие проверочных листов 320/390/768/1440 px, длинного контента и текста 200%; отсутствие loading/error-примеров действий. У EventCard/PostCard не было широкой компоновки, у WorkoutEntry — `Mobile / Summary` и `Desktop / Distance`. Эти пробелы закрыты в результате дизайна ниже.

## Согласованная общая модель

1. Сохранить исходные наборы, ID вариантов, визуальное направление и предметные состояния. Для EventCard/PostCard в названия исходных вариантов добавлена ось `Layout`; их ID не изменены.
2. Каждый компонент получает отдельную сериализуемую UI-схему в `openApi/frontend/`; TypeScript-модель генерируется. Callbacks, DOM-атрибуты, refs и router bindings остаются техническими props.
3. Компоненты только отображают подтверждённое состояние владельца и сообщают о действии наружу. Транспорт, права, оптимистические обновления, повтор запросов и продуктовые переходы относятся к R2–R5.
4. Высота определяется содержимым. Русский текст, длинные имена и непрерывные токены переносятся; полезный контент не скрывается только из-за ширины или увеличения текста.
5. Изменяющие действия — Button. Переход к уже доступному объекту — нативная ссылка с предоставленным адресом. Карточку с вложенными действиями не оборачивать целиком в ссылку.
6. Ошибка сохраняет предыдущее подтверждённое состояние и предлагает понятное восстановление. Loading блокирует повтор и конкурирующее действие компонента; спиннер заменяет содержимое активной кнопки без изменения размеров.

## Message

- Сохранить `Incoming`, `Sent`, `Sending`, `Failed`. Направление определяет выравнивание: входящее слева, исходящее справа; цвет остаётся дополнительным признаком, а подписи автора и статуса — текстовыми.
- Сообщение занимает не более 85% узкого контейнера и не более 42rem на широком. Короткое сообщение не растягивается на всю строку. Время и статус переносятся без наложения на текст.
- `Sending` означает неподтверждённую отправку. `Failed` показывает «Не отправлено» и кнопку «Повторить». Повтор лишь вызывает callback; компонент не утверждает, доставлена ли первая попытка.
- Текст сообщения отображается полностью. Ссылки и непрерывные строки переносятся; автоматическое распознавание ссылок, вложения, реакции, редактирование, удаление и read receipts не входят в FE-20.
- Новые сообщения и смена статуса не должны переносить фокус. Владелец списка управляет автопрокруткой и объявлением новых сообщений, чтобы компонент не создавал повторные live-region сообщения.

## EventCard

- Сохранить `Invited`, `Joined`, `Cancelled`; добавить `Layout=Stacked/Row` для каждой предметной версии. Узкая карточка складывает действие под содержимым, широкая размещает компактное действие справа при достаточной ширине контейнера.
- Обязательные данные представления: дата/время с машинным `dateTime`, отображаемая временная зона, название, место, число участников и состояние. Форматирование локали выполняет владелец; компонент не вычисляет дату и склонения.
- `Invited` — «Принять приглашение», `Joined` — ссылка «Открыть событие», `Cancelled` — без действия. Отклонение приглашения и выход из события не добавляются без продуктового решения R3.
- Для принятия показать loading и ошибку: «Не удалось принять приглашение. Попробуйте ещё раз». Успех отображается только после перехода владельца в `Joined`.

## PostCard

- Сохранить `Default` и `Liked`; добавить `Layout=Compact/Wide`. Лента остаётся одноколоночной: до 40rem контента, без растягивания текста на весь desktop.
- Отображать автора, опубликованное время, аудиторию, текст и число реакций. Время и подпись аудитории приходят готовыми строками; права видимости не вычисляются карточкой.
- Кнопка реакции имеет два программно различимых состояния и текст «Нравится · N». Счётчик приходит от владельца; карточка не увеличивает его самостоятельно.
- Для реакции показать loading и ошибку: «Не удалось изменить реакцию. Попробуйте ещё раз». При ошибке сохранить подтверждённые `liked` и count.
- Медиа, комментарии, репост, меню записи, сокращение длинной публикации и модерация остаются за R4. FE-20 не скрывает часть текста за неработающим «Ещё».

## WorkoutEntry

- Довести матрицу до шести вариантов: `Metric=Strength/Distance/Summary` × `Layout=Mobile/Desktop`. Исходные четыре варианта сохранить.
- В коде layout определяется шириной контейнера, а не пропом viewport: узкий контейнер показывает карточку, широкий — строку. Figma-варианты документируют оба результата.
- Strength: дата, упражнение, подходы, повторения, вес. Distance: дата, активность, дистанция, время. Единицы и отформатированные значения приходят от владельца; компонент не пересчитывает тренировочные данные.
- Summary: период, подпись «Сводка периода», последний результат, дата сжатия и дата последнего результата. Состояние не означает удаления истории и не даёт редактировать исходные записи.
- Для обычной записи действие «Изменить результат» доступно в обеих компоновках. Summary открывает сводку по ссылке или callback владельца; сетевой loading внутри записи не моделируется.
- На desktop использовать responsive grid, а не HTML-таблицу без заголовков. Если владелец собирает семантическую таблицу журнала, он отвечает за заголовки колонок и передаёт ячейки через отдельный адаптер; shared-компонент остаётся самостоятельной записью.

## План после визуальной приёмки

1. Создать четыре UI-схемы, сгенерировать модели и реализовать компоненты через существующие Avatar/Button/Icon; расширение Icon потребует отдельного согласованного набора.
2. Добавить каталог всех предметных и responsive-состояний, Light/Dark, loading/error и длинного контента. Демонстрационные переходы не считать контрактом backend.
3. Проверить callbacks/ссылки, блокировку повторных действий, фокус, клавиатуру, touch, 200% текста, forced colors и отсутствие переполнения. Цель покрытия собственного runtime-кода — 100% на файл по четырём метрикам; затем профильное frontend-review и UI/UX-review.

## Проверки текущего этапа

Программно проверены четыре component set: Message — 4 варианта, EventCard — 6, PostCard — 4, WorkoutEntry — 6. Подтверждена сохранность всех 13 исходных ID. Все 12 листов отрендерены; визуально просмотрены крайние сценарии 320 Light, 1440 Dark, Actions/Error Dark и Long content + 200% Light. Для каждого листа проверены явный режим темы, привязка фона/подписей к семантическим переменным, связи instances и отсутствие выхода верхнеуровневых секций за границы.

Новые переменные, стили и эффекты не добавлялись. Код не изменялся, поэтому сборки и тесты не запускались. Следующий шаг — визуальная приёмка перечисленных листов; только отдельное согласование после неё разрешит реализацию кода FE-20.

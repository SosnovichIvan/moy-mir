# Этапы, согласование и качество

## Обязательная последовательность пользователя

Дополнение пользователя: тесты всех сервисов и модулей стремятся к **100% покрытия собственного кода**; ≥90% остаётся минимальным допуском. [Методика и правила](testing.md). Тестирование выполняется вместе с кодом, не откладывается до финального этапа.

| Этап | Результат для согласования | Условие перехода |
| --- | --- | --- |
| 1. Аналитика | V1, развитие, сценарии, права, границы сервисов, открытые вопросы | Явное согласование пользователя |
| 2. Дизайн | Mobile-first прототипы, состояния, дизайн-система Tailwind, desktop-адаптация | Явное согласование дизайна |
| 3. DevOps | Стеки и ADR, окружения, релизы frontend/core/identity/media, reverse proxy, фоновые задания, CI/CD, секреты, наблюдаемость, восстановление | Проверка и согласование |
| 4. Модели БД | Посервисные схемы, миграции, генераторы, индексы, права, хранение/удаление; контракты данных | Ревью БД и согласование |
| 5. Backend | Утверждённые API/события, генерация, сервисы, авторизация и интеграции | Проверки и согласование backend |
| 6. Frontend | Единый frontend с внутренними разделами, PWA и сценарии по дизайну | Ревью и согласование frontend |
| 7. Покрытие | Не менее 90% покрытия собственного кода и критические сценарии | Проверенный отчёт CI |
| 8. Финальное ревью | Ревью frontend/backend/БД своими скилами, исправления и повторная проверка | Итоговая приёмка |

Текущая разрешённая работа: дизайн по прямым запросам пользователя на создание тем и логотипа. Утверждено только направление 02 со светлой и тёмной темами; это не означает закрытия всех вопросов аналитики или согласования полного дизайна. Порядок задан пользователем; скилы его не отменяют. Аналитические списки сущностей — не физические схемы БД. API-спецификации и код генераторов появятся на соответствующих этапах после утверждения зависимостей.

Тесты пишутся по мере реализации; отдельный этап покрытия доводит полноту до обязательного порога. Предложенный способ измерения: для каждого активного сервиса и каждого внутреннего модуля backend/frontend не менее 90% lines, statements, functions и branches (либо сопоставимые поддерживаемые метрики стека); общий процент не скрывает слабый модуль. Генерируемый код, зависимости и статические assets исключаются явно; собственная предметная логика не исключается для достижения числа. Генерацию проверять воспроизводимостью, компиляцией и контрактными тестами.

Обязательно независимо от процента: авторизация, отзыв доступа, повторы команд, гонки участия, отмена/перенос события, часовые пояса, WebSocket reconnect, принятие редакции программы, отчёты, ошибка загрузки раздела, сжатие журнала, повторяющиеся тренировки, права друга-модератора, большие группы, файловые права, выход из аккаунта, upgrade/rollback PWA. Unit + интеграционные + контрактные + E2E, посервисные coverage artifacts. CI должен блокировать неподтверждённые изменения generated-кода, несовместимые контракты и падение порога. Проверка backup/restore не заменяется unit-тестом.

# Архитектура старта и дальнейшее разделение

Дата: 2026-09-15. Правки пользователя приняты в части состава развёртывания. Технологии и детали ниже — предложения; реализация отсутствует. [Первоначальное предложение](history/2026-09-15-initial-proposal.md) сохранено как superseded.

## Основания

До 5000 пользователей на старте, аудитория — Россия, без монетизации. Группы могут быть большими и существовать независимо от событий. Общение — самостоятельная функция. Mobile first, PWA, Tailwind, генерация всех моделей и контракты в `openApi/` сохраняются. Отдельная роль тренера заменена назначением друга модератором тренировок.

5000 пользователей не означают 5000 одновременных сессий. Пиковые подключения, сообщения в секунду, размер большой группы, объём файлов и бюджет пока неизвестны. Нагрузочный профиль и ресурсы согласуются на DevOps-этапе. Россия — география запуска; размещение основного хранилища, резервных копий и журналов требуется определить отдельно.

## ADR-001: общий backend и frontend

**Статус: accepted в части границ развёртывания**, по прямой правке пользователя. Конкретные стеки и внутренние границы — proposed.

Варианты: отдельные предметные микросервисы и runtime MFE увеличивают число релизов и сетевых отказов; общий сервис без внутренних границ затрудняет разделение. Выбраны модульный основной backend и единый модульный frontend. Отдельно развёртываются backend авторизации и backend хранения файлов.

| Единица развёртывания V1 | Ответственность | Данные |
| --- | --- | --- |
| frontend | Общее приложение, навигация, PWA, разделы social/planner/messenger/training/collaboration | Только клиентское состояние; не владелец предметных данных |
| core | Профили, друзья, группы, лента, планы, события, сообщения, тренировки, журнал, запросы, отчёты, уведомления | Основная БД с логическим владением по модулям |
| identity | Регистрация, аутентификация, восстановление, сессии и отзыв учётных данных | Отдельная БД учётных записей и сессий |
| media | Загрузка, хранение, чтение и удаление файлов; технические метаданные и жизненный цикл | Отдельная БД метаданных и закрытое объектное хранилище |

Identity — отдельный сервис авторизации в терминологии проекта. Проверка прав на событие, группу, журнал или отчёт остаётся в core: успешный вход не означает доступ к любой сущности. Identity хранит идентификатор и данные входа; публичное имя, аватар и социальный профиль принадлежат core/community.

Кандидаты до утверждения DevOps: TypeScript + NestJS и PostgreSQL для core; React + TypeScript + Tailwind для frontend; identity на готовом OIDC-решении либо отдельной интеграционной службе; media с PostgreSQL для метаданных и S3-совместимым хранилищем. Провайдеры и версии не выбраны. Для текущих связных данных PostgreSQL проще, чем несколько разных БД; отдельный стек вводится по задаче и результатам измерений.

## Внутренние модули core

| Модуль | Владеет | Контракты |
| --- | --- | --- |
| community | Профили, друзья, блокировки, группы, роли, записи, реакции | `openApi/core/community/` |
| planning | События, участие, подписки, личные планы, календарные разрешения и проекция тренировок | `openApi/core/planning/` |
| communication | Личные диалоги, чаты событий, сообщения, прочитанность | `openApi/core/communication/` |
| training | Разовые занятия, серии и исключения, программы, права модераторов, журнал и сводки сжатия | `openApi/core/training/` |
| collaboration | Запросы, результаты, внутренние отчёты и получатели | `openApi/core/collaboration/` |
| notifications | Уведомления, предпочтения и надёжные задания доставки | `openApi/core/notifications/` |

Это модули **одного процесса и релиза**, а не отдельные сетевые сервисы. Данные физически могут находиться в одной БД, но каждый модуль владеет своими таблицами/схемой и миграциями. Другие модули обращаются к его публичному интерфейсу, не импортируют репозитории и ORM-сущности, не пишут в чужие таблицы. Межмодульные JOIN и внешние ключи не вводить без ADR с объяснением будущего разделения. Обмен моделями — только через генерацию из общих схем.

Разрешённые зависимости: planning/training → community; communication → community/planning; collaboration → community/planning/training. Notifications получает события и перед показом приватных деталей вызывает владельца прав. Planning получает расписание training через события; обратный синхронный вызов training → planning не требуется. Адаптер identity общий технический интерфейс, без дублирования предметных прав.

## ADR-002: сеть и фоновые операции

Статус: proposed, заменяет обязательный mesh первоначального предложения.

Поток: браузер → HTTPS reverse proxy → frontend/core/identity/media. Core вызывает identity/media через их API при необходимости. Внутри core — вызовы интерфейсов в памяти, без сетевых шлюзов между модулями. Отдельного прикладного gateway/BFF-процесса в V1 нет: агрегация принадлежит входному слою core. Reverse proxy — инфраструктурный компонент.

Kubernetes, Istio и брокер не обязательны для старта. Конкретная платформа выбирается по ресурсам и эксплуатации. Фоновые задания предлагается хранить в БД; worker использует код core, при необходимости запускается отдельным процессом той же сборки, не становится самостоятельным предметным сервисом.

Владелец сохраняет изменение и outbox в одной транзакции. Обработчик хранит ID выполненного задания, ограниченно повторяет неудачи и помещает исчерпанные в наблюдаемую очередь ошибок. Повтор команды с ключом идемпотентности не дублирует результат. При будущем выделении сервисов outbox подключается к брокеру, локальный адаптер заменяется сетевым. Между identity, media и core общей транзакции нет.

## ADR-003: единый frontend и PWA

Статус: accepted для единого frontend; детали реализации proposed. Runtime MFE и независимые frontend-релизы отложены до необходимости разделения.

Shell, social, planner, messenger, training и collaboration — внутренние модули одной сборки. Разделы подгружаются по маршрутам из assets одного релиза. Общие токены Tailwind и UI-компоненты версионируются вместе с приложением; нет удалённого MFE manifest. Модули общаются через публичные интерфейсы, маршруты и генерируемые модели; не импортируют внутреннее состояние друг друга.

PWA устанавливается как одно приложение. В V1 кешируются оболочка и публичные версионированные assets; приватные API-ответы, чаты и отчёты не доступны offline. Ошибка загрузки раздела локальна, навигация сохраняется. При обновлении не терять заполненную форму; сохранять assets прежнего релиза на период активных сессий. Выход очищает приватное состояние клиента. Установка, обновление и откат проверяются на целевых браузерах на frontend-этапе.

При будущем MFE-разделении понадобятся отдельные релизы, manifest, совместимость shared-зависимостей и изоляция стилей. Сейчас это не реализуется и не считается обязательной инфраструктурой.

## Файлы в V1

Подтверждено: media — отдельный backend уже на старте. Продуктовые точки загрузки пока не определены. Предложенный минимальный потребитель — аватары пользователей и изображения групп; вложения сообщений/записей остаются расширением, пока не согласованы. Отдельный файловый сервис не включает экспорт отчётов: отчёты создаются и читаются внутри приложения, скачивания PDF нет.

Core решает, кому доступен связанный объект. Media проверяет пользователя и разрешение на конкретную операцию, выданное core; произвольный object ID не даёт права чтения. Для приватных файлов предложено проксированное чтение с актуальной проверкой доступа. Длительно живущие публичные URL для приватных файлов не выдаются. Хранилище закрыто от прямого доступа браузера.

Загрузка: проверка разрешения и лимита → временный объект → проверка размера/типа и завершённости → регистрация метаданных → привязка в core. Незавершённые и непривязанные загрузки очищаются по согласованному сроку. Повтор завершения безопасен; временный сбой core не публикует объект автоматически. Удаление инициируется владельцем предметной сущности и повторяется до подтверждения media. Лимиты, проверка содержимого и срок очистки фиксируются перед реализацией.

## Сценарии, согласованность и отказы

1. **Общение без события:** communication сохраняет личное сообщение после проверки дружбы/блокировки; клиент получает подтверждение только после записи. После разрыва история восстанавливается по курсору; клиентский ID предотвращает дубли.
2. **Большая группа:** community владеет членством и ролями. Списки и лента постраничные; нельзя загружать весь состав на каждый запрос. Уведомления большой группе доставляются ограниченными пакетами. Нагрузочная проверка включает перекос активности в одной группе, а не только равномерные 5000 аккаунтов.
3. **Событие:** planning атомарно меняет участие и outbox; уведомление может прийти позже. Подписка не означает участие. Communication перепроверяет права при чтении, отправке и подключении; отзыв доступа закрывает действующий чат.
4. **Повторяющаяся тренировка:** training владеет серией, экземплярами и исключениями. Planning хранит календарную проекцию по ID/версии; старое событие не возвращает устаревший план. Изменение будущей серии сохраняет выполненные занятия.
5. **Сжатие журнала:** training проверяет владельца либо права назначенного друга, выбранный диапазон и версии исходных записей; сохраняет сводку, дату операции и последние результаты по упражнениям. Предложено сохранять исходные записи; конкурентная правка не должна молча попадать в частичную сводку. Подробная семантика — в продуктовом документе.
6. **Отчёт:** collaboration хранит отправленную редакцию и получателей; публикация в ленту отдельная. Изменение/сжатие исходного журнала не меняет ранее отправленный отчёт. Чтение проверяет текущие права.
7. **Удаление аккаунта:** identity отзывает вход, core очищает/анонимизирует предметные данные, media удаляет объекты с подтверждениями и повторами. Политики хранения переписки и резервных копий нужно согласовать до БД.

Недоступность проверки прав означает отказ в приватной операции. Нужны корреляция запросов, метрики ошибок, логи без токенов и содержимого переписок, аудит выдачи/отзыва доступа, таймауты и безопасные повторы сетевых вызовов. Нет оснований обещать SLA или выдерживаемое число соединений до измерений.

## Готовность к выделению сервисов

Выделение определяется конкретным ограничением нагрузки, независимым циклом релизов или ответственностью команды. Общая БД core и совместное развёртывание его модулей — осознанный компромисс стартовой архитектуры; границы модулей облегчают, но не делают разделение бесплатным.

Порядок: зафиксировать контракт → проверить отсутствие обходных зависимостей → подготовить отдельное хранилище и backfill → сверить данные → переключить публичный адаптер и единственного владельца записи → проверить контрактные тесты и нагрузку → вывести старый путь. На cutover нужен план короткой остановки записи либо переноса изменений; избегать неуправляемой двойной записи. До включения записи в новом владельце можно откатить маршрутизацию; после неё необходим перенос новых данных обратно. Миграции только расширяющие до завершения отката.

Frontend выделяется по публичной границе раздела с тестом совместимости оболочки; backend-разделение не требует одновременного выделения frontend.

## Открыто перед DevOps

Пиковая активность и WebSocket-соединения, максимальный размер группы, файловые лимиты и потребители, бюджет, команда, хостинг и регион хранения, способ входа, браузеры, целевые задержки, доступность и восстановление RPO/RTO. Для проверки: согласованный профиль до 5000 пользователей, сценарий большой группы, длинный журнал, повторы, резервное копирование и восстановление. Это критерии будущей проверки, не результаты тестов.

## Уточнение продуктовых релизов · 2026-09-18

Термин V1 выше описывает стартовую архитектуру. Продукт поставляется последовательно по [R1–R5](../product/release-roadmap.md); единого выпуска всех предметных функций больше не планируется. Общая сборка не означает один продуктовый релиз за всё время. Раздельные identity/media и внутренние границы core/frontend сохраняются.

# Архив первоначального предложения

Статус: superseded. Не использовать как действующее требование. Заменён [текущей архитектурой](../proposal.md) после правок пользователя: общий backend и frontend, отдельные авторизация и файлы. Ни один вариант не реализован.

# Архитектурное предложение

Статус: proposed. Дата: 2026-09-15. Это аналитика, не утверждённый стек и не готовый DevOps-проект.

## Подтверждённые ограничения

Mobile first, PWA, Tailwind; отдельно развёртываемые backend-сервисы и frontend MFE; загрузка необходимых модулей; межсервисное взаимодействие через управляемую сетевую инфраструктуру; стек и БД по задаче сервиса; общие контракты в `openApi`; только генерируемые модели; посервисная документация и контексты агентов.

## ADR-001: границы и эксплуатационная сложность

Варианты: модульный монолит проще обслуживать, но не выполняет требование независимых backend-сервисов; десятки мелких сервисов увеличат число сетевых отказов и стоимость поддержки. Предложение — семь активных предметных/поддерживающих сервисов V1 и один API gateway/BFF (адаптер запросов для интерфейса), отдельные процессы с собственными данными. Один репозиторий упрощает согласованные изменения контрактов; релизы и сборки раздельные.

| Сервис | Владеет | Предлагаемый старт | Обоснование |
| --- | --- | --- | --- |
| identity | Профиль, идентификатор пользователя, сессии, интеграция входа | TypeScript + NestJS, PostgreSQL, OIDC-провайдер | Учётные записи не смешиваются с дружбой; поставщика входа выбрать отдельно |
| community | Дружба, блокировки, группы, роли, посты и реакции | TypeScript + NestJS, PostgreSQL | Связи и права требуют транзакций; лента пилота без отдельного поискового движка |
| planning | События, участники, подписки, планы, права календаря, календарная проекция | TypeScript + NestJS, PostgreSQL | Одна транзакция для изменения состава события; календарь не второй владелец события |
| communication | Личные диалоги и чаты событий, сообщения, отметки прочтения | TypeScript + NestJS, PostgreSQL | Сохраняемая история; WebSocket для доставки, HTTP для восстановления |
| training | Упражнения, занятия, программы, доступ тренера, редакции и результаты | TypeScript + NestJS, PostgreSQL | Связанные сущности и версионирование плана |
| collaboration | Запросы на работу, состояния исполнения, отчёты, получатели | TypeScript + NestJS, PostgreSQL | Одинаковый жизненный цикл «запрос — результат — передача» для разных областей |
| notifications | Внутренние уведомления, предпочтения, задания доставки | TypeScript + NestJS, PostgreSQL | Надёжная очередь и дедупликация; каналы можно добавлять позднее |
| media | Метаданные файлов, права, загрузка и удаление объектов | Отложен после V1 | В V1 текст и инициалы; объектное хранилище вводится с вложениями |

Уточнение количества: V1 содержит **семь активных backend-сервисов плюс gateway**, media — будущий восьмой. Физические каталоги и процессы создаются на соответствующем согласованном этапе, сейчас созданы только контексты.

PostgreSQL предлагается для всех активных предметных сервисов из-за транзакционных связей текущих сценариев, а не как обязательная БД для любого будущего сервиса. Каждому сервису — отдельная БД и учётная запись; допустим общий кластер на пилоте. Чужие таблицы и межсервисные SQL JOIN запрещены. Redis не источник истины и добавляется только при доказанной потребности в presence, rate limits или распределённом fan-out. MongoDB/графовая БД/отдельный поиск пока не имеют подтверждённой задачи.

Альтернатива для communication — Go при подтверждённом ограничении ресурсов на большое число соединений; цена — второй toolchain и второй набор генераторов. Для аналитических задач позднее возможен Python. Выбор пересматривать по измерениям и компетенциям команды. Версии инструментов фиксировать на этапе DevOps после проверки совместимости, не брать `latest` в релизы.

## ADR-002: сеть, шлюзы и доставка событий

Поток: браузер → HTTPS API gateway/BFF → внутренний сервис → его БД. Межсервисные HTTP-вызовы проходят через управляемые прокси/service mesh; асинхронные сообщения — через брокер, доступный по внутренним политикам. Браузер не обращается к БД, брокеру и внутренним адресам.

API gateway и mesh решают разные задачи. Первый обеспечивает внешний вход и маршрутизацию; mesh — политику и защиту связи сервисов. Не требуется возвращать каждый внутренний запрос во внешний шлюз. Istio поддерживает маршрутизацию внутри mesh и gateway-конфигурацию: [официальная документация](https://istio.io/latest/docs/concepts/traffic-management/).

Предлагаемый production-кандидат — Kubernetes + Istio, внешний gateway и OIDC-провайдер. Альтернатива — более лёгкая платформа с внутренними шлюзами/прокси и теми же политиками. Решение зависит от бюджета и оператора; не утверждаем кластер до ответа. Локально — контейнерный запуск; для проверки mesh нужен отдельный интеграционный профиль. DevOps-этап должен зафиксировать topology, TLS/mTLS, секреты, CI/CD, backup/restore, телеметрию и стоимость.

Для фоновых событий — кандидат RabbitMQ. Смена брокера допустима до утверждения DevOps. Владелец записывает бизнес-изменение и outbox в одной транзакции; worker доставляет событие, потребитель хранит обработанный ID. Доставка как минимум один раз, внешние эффекты идемпотентны. Ограниченные повторы с задержкой, очередь ошибок, ручной replay с аудитом. Согласовать пределы задержки и оповещения, не обещать мгновенную согласованность ленты и уведомлений.

## ADR-003: MFE и PWA

Shell — отдельно развёртываемая оболочка с авторизацией, навигацией, PWA manifest, service worker, каталогом разрешённых MFE и общими токенами. Установка PWA относится к оболочке; установка функционального модуля означает загрузку и подключение frontend-пакета, а не развёртывание backend для каждого пользователя.

Предложенные MFE:

| Модуль | Область |
| --- | --- |
| social | Друзья, группы, лента |
| planner | Сегодня, календарь, события и личные планы |
| messenger | Личные диалоги и обсуждение события |
| training | Тренировки, программы, работа с тренером |
| collaboration | Запросы и отчёты |

Для всех стартовый кандидат React + TypeScript + Tailwind; runtime Module Federation. Другой framework возможен по ADR с оценкой веса, доступности и совместимости; одинаковые сценарии не обосновывают разные стеки. Полностью статическая сборка проще, но не соответствует требованию динамического подключения. Module Federation позволяет описывать remote через manifest: [документация](https://module-federation.io/guide/basic/manifest-snapshot).

Shell загружает только нужный remote; версии immutable, manifest публикуется атомарно и имеет список разрешённых адресов. Согласованный диапазон shared-зависимостей, контракт mount/unmount, маршрутов и событий; CSS reset принадлежит shell, модульные стили изолированы. Общая дизайн-система версионируется. MFE не импортируют внутренности друг друга и не разделяют глобальное предметное состояние. Отказ remote показывает ошибку в его области; shell и другие маршруты остаются доступны. Старые assets сохраняются на время активных сессий, предусмотрен откат manifest.

HTTPS, web manifest и браузерная поддержка определяют установку PWA; offline — отдельная возможность: [MDN, установка](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable), [MDN, offline](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation). В V1 service worker кеширует публичную оболочку и версионированные assets. Приватные ответы API, чаты и отчёты не кешируются для offline. Logout очищает клиентское состояние. Нельзя активировать несовместимое обновление shell посреди заполнения формы. Матрица установки и обновления проверяется на реальных целевых браузерах на этапе frontend.

## Владение и разрешённые зависимости

Identity проверяет личность; community — дружбу, блокировки и членство; planning — события и участие; training — программу и полномочия тренера; collaboration — адресатов отчёта. Gateway не заменяет предметную авторизацию.

Направление синхронных проверок: community → identity; planning → community/identity; training → community/identity; communication → planning/community/identity; collaboration → training/planning/community/identity. Notifications читает события и проверяет актуальные права у источника перед показом приватных деталей. Обратные вызовы из источника в производный сервис не нужны: используются события. Planning получает изменения назначенных тренировок асинхронно; training не зависит синхронно от planning. Так исключается цикл training ↔ planning.

Недоступность владельца прав означает отказ в доступе к приватной операции, а не разрешение по устаревшему кешу. Календарь может хранить проекцию, но перед выдачей чужих деталей проверяет текущие разрешения. Идентификатор из URL не доказательство доступа. Чат перепроверяет права на каждую операцию; событие отзыва закрывает соединение, проверка чтения/отправки защищает и при задержке этого события.

## Ключевые потоки и отказы

1. **Участие:** shell/planner → gateway → planning; проверка доступа и атомарное добавление участника + outbox. Повтор с тем же ключом идемпотентности возвращает прежний результат. Notifications получает событие позднее. Недоступность брокера не откатывает успешное участие; outbox ждёт восстановления.
2. **Сообщение:** messenger → gateway → communication; проверка прав у владельца → запись сообщения с клиентским ID → доставка online. Подтверждение отправки только после сохранения. При разрыве клиент получает историю по курсору; дедупликация не позволяет повторить сообщение.
3. **Программа:** training сохраняет принятую редакцию и outbox. Planning обновляет проекцию по ID/версии занятия. Позднее старое событие не откатывает новую версию; удаление передаётся tombstone-событием. При задержке проекции UI сообщает, что расписание обновляется.
4. **Отчёт:** collaboration проверяет право автора на источник, сохраняет снимок результата и выбранных получателей, создаёт outbox. Неудачная доставка уведомления не создаёт второй отчёт. При каждом открытии проверяется текущий доступ; уведомление само по себе не содержит приватный результат.
5. **Удаление аккаунта:** identity инициирует процесс; каждый владелец очищает/анонимизирует свои данные с подтверждением. Оркестрация и повторяемость обязательны; сроки и судьба чужих переписок требуют отдельного решения до БД.

В каждом сервисе: timeout на исходящие запросы, корреляционный ID, структурированные логи без сообщений/токенов, метрики ошибок и задержек, health/readiness, аудит изменений доступа. Общих транзакций БД между сервисами нет. Для критической синхронной операции возвращается понятная ошибка и возможность безопасного повтора.

## Что надо решить перед инфраструктурой

Ожидаемые пользователи и concurrent-соединения; размер команды; бюджет; окружения и хостинг; способ входа и доставки приглашений; целевые браузеры; требования к восстановлению RPO/RTO, доступности и latency; хранение/удаление данных. Числа неизвестны. На DevOps-этапе нужны утверждённый нагрузочный профиль, замер и проверка восстановления; без них нельзя заявлять обеспеченную ёмкость и SLA.
